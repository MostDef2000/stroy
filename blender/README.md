# Blender Renderer

Blender is a deterministic execution/render backend, not canonical storage.

## Canonical boundary

The home worker receives an immutable canonical Scene snapshot plus:

- exact scene revision ID;
- optional design revision ID;
- canonical camera ID;
- renderer profile.

`stroy.rendering.build_blender_plan` converts millimetres to metres, copies canonical transforms, assigns stable semantic object/material indices, and converts `fx/fy/cx/cy` into Blender camera settings. The resulting plan is deterministic JSON. No project state exists only in a `.blend` file.

The Blender subprocess is always started with `--background --factory-startup`. The checked-in entrypoint is `blender/stroy_blender.py`.

## Golden room

With Blender installed:

```bash
make render-golden
```

This renders `fixtures/golden-room.scene.json` into `renders/golden-room/`.

For a geometry-only smoke test:

```bash
python3 scripts/render_golden_room.py --build-only
```

The build-only path still launches Blender headlessly and writes deterministic `scene_metadata.json`.

## Manual bare-twin benchmark (issue #21)

`scripts/benchmark_bare_twin.py` is a manual, non-CI harness that measures bare
apartment render cost across renderer profiles on the GPU box:

```bash
python3 scripts/benchmark_bare_twin.py --profiles blender-eevee-v0,blender-cycles-gpu-v0
```

It renders the synthetic `fixtures/bare-twin-bench.scene.json` (no owner
geometry) for each profile x camera x run, recording wall time and peak
`nvidia-smi` VRAM into `renders/bench/bare-twin/benchmark.{json,md}`. Run index
0 is reported as cold and later runs as warm. Use `--build-only` to launch
Blender without rendering. If Blender is not found the harness exits with a
clear message; set `STROY_BLENDER_BIN=/path/to/blender` to point at it.
`blender-cycles-gpu-v0` selects GPU Cycles (OPTIX with CUDA fallback), while
`blender-cycles-v0` keeps the CPU Cycles behaviour used by production/CI.

## Control-pass contract

All five render passes use the same canonical camera, resolution and scene state.

| Pass | File | Contract |
| --- | --- | --- |
| RGB | `rgb.png` | Combined Cycles preview |
| Depth | `depth.exr` | Blender Z pass; distance to nearest visible surface in metres |
| Normals | `normals.exr` | World-space surface normals, float RGB |
| Object IDs | `object_ids.exr` | Exact stable non-zero integer object index stored as float |
| Material IDs | `material_ids.exr` | Exact stable non-zero integer material index stored as float |

One Blender unit equals one metre. The camera near/far clip range is `0.01m .. 1000m`. For depth consumers, values outside that interval are invalid/background. Object/material background is ID `0`.

Object/material IDs are derived deterministically from canonical semantic IDs/material refs and limited to 24-bit positive integers, which remain exactly representable in 32-bit float EXR channels.

Cycles is used for the v0 control profile because Object Index and Material Index render passes are required. The v0 control renderer explicitly uses CPU Cycles so those index passes remain available consistently. RGB, depth, normals and the two index passes are generated by the same render invocation.

## Outputs

The worker uploads every output as a derived Asset tagged with its semantic pass name. After upload, it finalizes a `RenderManifest` containing Asset IDs and the exact revision/camera/profile provenance. The API validates and persists that manifest.

Generated `.blend` files are optional debugging/cache artifacts and are never canonical.


CI installs Blender, performs a real low-resolution headless golden-room render, opens every produced PNG/EXR back through Blender, and asserts identical pixel dimensions for all five passes.
